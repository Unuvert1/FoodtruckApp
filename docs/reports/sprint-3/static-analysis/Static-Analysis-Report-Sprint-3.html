5. Reflection

The most problematic area is the third-party dependency chain rather than the team's own code: all 14 vulnerabilities, including every one of the 8 HIGH findings, come from transitive packages, and two thirds trace back to just two entries in package.json — the shadcn CLI, declared as a runtime dependency although it is only ever used to scaffold components, and Next.js, which pins an outdated postcss internally. To reduce this next sprint we will move shadcn into devDependencies and upgrade Next.js to 15.5.27 — together these clear 10 of the 14 findings — then add a Trivy step to CI so a vulnerable dependency fails the build instead of waiting for an end-of-sprint scan. On the code-quality side the project is clean for reliability and security (0 bugs, 0 vulnerabilities), so the remaining work is maintainability: splitting the five functions that exceed the cognitive complexity limit and replacing the 24 nested ternary expressions, which are the single largest source of code smells.

Issue types follow each rule's published RSPEC classification. S5852 is defined as “security-sensitive”, which is a Security Hotspot — an item requiring human review rather than a confirmed defect. The other five are maintainability rules.

Security hotspot review

A Security Hotspot requires a developer to review the surrounding context and record a verdict. Both were reviewed by tracing the data that reaches each regular expression.

components/dashboard/onboarding-form.tsx:25

Make sure the regex used here, which is vulnerable to super-linear runtime due to backtracking, cannot lead to denial of service.

.replace(/[^a-z0-9]+/g, "-")
.replace(/^-+|-+$/g, "")
.slice(0, 40);

Verdict: not exploitable. This is slugify inside onboarding-form.tsx, a "use client" component: the expression runs in the visitor's own browser, on the truck name they are typing into their own form, and the result is truncated to 40 characters. /-+$/ can degrade to quadratic time on a long run of dashes, but the only machine affected is the typist's own browser tab. No server-side request evaluates this expression, so there is no denial-of-service surface.

lib/money.ts:71

Make sure the regex used here, which is vulnerable to super-linear runtime due to backtracking, cannot lead to denial of service.

const fraction = String(bps % 100).padStart(2, "0").replace(/0+$/, "");

Verdict: not exploitable. bps % 100 is an integer between 0 and 99, so after padStart(2) the subject string is always exactly two characters. /0+$/ cannot backtrack meaningfully over two characters, and the input is a computed value rather than user-supplied data.

Both hotspots are reviewed and accepted, satisfying the “security hotspots reviewed” gate condition. They were left unchanged rather than rewritten, since rewriting code with no reachable risk is churn; if either expression moves to the server, the verdict must be revisited.
