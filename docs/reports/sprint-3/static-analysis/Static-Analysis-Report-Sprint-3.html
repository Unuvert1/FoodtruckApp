EditionNot SonarQube Server or SonarQube Cloud — the same rule engine, run locally. See the note below.
Why SonarJS and not the SonarQube server. The SonarQube Server and Cloud products run these same SonarJS rules behind a web dashboard. Neither could be run on this machine within the sprint: the server edition needs Docker, and Docker Desktop's engine requires WSL2, which is not installed here and needs administrator rights plus a reboot to add. SonarQube Cloud is free for public repositories like this one, but importing the project needs a GitHub authorization the team has not yet granted. The rules, the rule identifiers (RSPEC numbers) and the issue classifications in this report are therefore the genuine SonarSource ones, executed over the whole codebase; what is missing is the hosted dashboard and its server-side Quality Gate. The gate in section 2 is evaluated locally against the published “Sonar way” conditions and is labelled as such.

5. Reflection

The most problematic area is not our own code but the third-party dependency chain: all 14 vulnerabilities, including every one of the 8 HIGH findings, come from transitive packages, and two thirds of them trace back to just two entries in package.json — the shadcn CLI, which is listed as a runtime dependency although it is only ever used as a scaffolding command, and Next.js, which pins an old postcss internally. To reduce this next sprint we will move shadcn out of dependencies and upgrade Next.js to 15.5.27, which together clear 10 of the 14 findings, then add a Trivy step to CI so a vulnerable dependency fails the build instead of waiting for a sprint-end scan. On the Sonar side the code is clean for reliability and security — 0 bugs and 0 vulnerabilities — so the work there is maintainability: splitting the five functions that exceed the complexity limit (the POS screen and the stop sheet worst of all, at 27 and 23 against a limit of 15) and replacing the 24 nested ternaries, which are the single largest cause of smells.
